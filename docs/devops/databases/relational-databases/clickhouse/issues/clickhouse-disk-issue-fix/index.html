clickhouse-disk-issue-fix

Date: 2026-02-02
Cluster: sandbox/oip-cluster
Namespace: oip
Pod: clickhouse-shard0-0

Problem Summary​

ClickHouse was experiencing disk space exhaustion, causing NOT_ENOUGH_SPACE errors that prevented normal operations including writing to system logs.

Symptoms Observed​

  • ClickHouse logs showing repeated errors: 
    Code: 243. DB::Exception: Cannot reserve 1.00 MiB, not enough space. (NOT_ENOUGH_SPACE)
  • System log tables (trace_log, text_log, metric_log, etc.) failing to flush
  • Disk usage at 100% (20GB PVC completely full with only 3.1MB available)

Root Cause​

ClickHouse system logging tables were growing without any TTL (Time-To-Live) configured, causing unbounded data retention:

TableSizeRow CountDate Range
system.trace_log16.80 GiB786,145,2357 days (Jan 27 - Feb 2)
system.text_log1.93 GiB10,459,44324 days (Jan 9 - Feb 2)
system.metric_log378.20 MiB--
system.asynchronous_metric_log268.88 MiB--

The trace_log table alone consumed 84% of the total disk space (16.8GB out of 20GB).

Why This Happened​

  1. No TTL configured by default: Bitnami ClickHouse Helm chart deploys ClickHouse without TTL on system tables
  2. High tracing activity: The trace_log table was generating ~112 million rows per day
  3. Small PVC size: 20GB is insufficient for ClickHouse workloads without proper data retention policies

Resolution Steps​

1. Emergency Space Recovery (Manual File Deletion)​

Since ClickHouse commands failed due to disk being 100% full, we had to delete data files directly:

# Deleted oldest trace_log partitions to free up space
kubectl exec clickhouse-shard0-0 -n oip -c clickhouse -- sh -c \
  'rm -rf /bitnami/clickhouse/data/store/f29/f2967280-0409-4813-aeec-e46588905c75/202601_107638_114235_7'

2. Truncate System Log Tables​

Once we had enough space, we truncated the problematic tables:

kubectl exec clickhouse-shard0-0 -n oip -c clickhouse -- \
  clickhouse-client --password '<password>' --query "TRUNCATE TABLE system.trace_log"

kubectl exec clickhouse-shard0-0 -n oip -c clickhouse -- \
  clickhouse-client --password '<password>' --query "TRUNCATE TABLE system.text_log"

kubectl exec clickhouse-shard0-0 -n oip -c clickhouse -- \
  clickhouse-client --password '<password>' --query "TRUNCATE TABLE system.metric_log"

kubectl exec clickhouse-shard0-0 -n oip -c clickhouse -- \
  clickhouse-client --password '<password>' --query "TRUNCATE TABLE system.asynchronous_metric_log"

3. Configure TTL on System Tables​

Applied TTL policies to prevent future disk exhaustion:

-- trace_log: High volume, keep 3 days only
ALTER TABLE system.trace_log MODIFY TTL event_date + INTERVAL 3 DAY;

-- Other system logs: Keep 7 days
ALTER TABLE system.text_log MODIFY TTL event_date + INTERVAL 7 DAY;
ALTER TABLE system.metric_log MODIFY TTL event_date + INTERVAL 7 DAY;
ALTER TABLE system.asynchronous_metric_log MODIFY TTL event_date + INTERVAL 7 DAY;
ALTER TABLE system.latency_log MODIFY TTL event_date + INTERVAL 7 DAY;
ALTER TABLE system.error_log MODIFY TTL event_date + INTERVAL 7 DAY;
ALTER TABLE system.query_log MODIFY TTL event_date + INTERVAL 7 DAY;
ALTER TABLE system.part_log MODIFY TTL event_date + INTERVAL 7 DAY;

Final State After Fix​

Filesystem      Size  Used Avail Use%
/dev/nvme3n1     20G  324M   20G   2%
  • Disk usage reduced from 100% to 2%
  • All system tables now have TTL configured
  • ClickHouse operations resumed normally

Recommendations for Long-Term Prevention​

1. Update Helm Values to Include TTL Configuration​

Add to your ClickHouse Helm values:

extraOverrides: |
  <clickhouse>
    <trace_log>
      <database>system</database>
      <table>trace_log</table>
      <ttl>event_date + INTERVAL 3 DAY</ttl>
    </trace_log>
    <query_log>
      <database>system</database>
      <table>query_log</table>
      <ttl>event_date + INTERVAL 7 DAY</ttl>
    </query_log>
    <text_log>
      <database>system</database>
      <table>text_log</table>
      <ttl>event_date + INTERVAL 7 DAY</ttl>
    </text_log>
  </clickhouse>

2. Consider Increasing PVC Size​

For production workloads, consider:

  • Increasing PVC to 50-100GB
  • Setting up disk usage monitoring/alerting at 70% threshold

3. Set Up Monitoring​

Add Prometheus alerts for ClickHouse disk usage:

- alert: ClickHouseDiskSpaceLow
  expr: clickhouse_disk_used_bytes / clickhouse_disk_total_bytes > 0.7
  for: 5m
  labels:
    severity: warning
  annotations:
    summary: "ClickHouse disk usage above 70%"

4. Disable Unnecessary Tracing (Optional)​

If trace_log is not needed, disable it in ClickHouse config:

<trace_log remove="1"/>

Useful Commands for Future Reference​

# Check disk usage
kubectl exec clickhouse-shard0-0 -n oip -c clickhouse -- df -h /bitnami/clickhouse

# Check table sizes
kubectl exec clickhouse-shard0-0 -n oip -c clickhouse -- \
  clickhouse-client --password '<password>' --query \
  "SELECT database, table, formatReadableSize(sum(bytes_on_disk)) as size 
   FROM system.parts WHERE active GROUP BY database, table 
   ORDER BY sum(bytes_on_disk) DESC LIMIT 20"

# Check TTL settings
kubectl exec clickhouse-shard0-0 -n oip -c clickhouse -- \
  clickhouse-client --password '<password>' --query \
  "SELECT database, name, engine_full FROM system.tables 
   WHERE database = 'system' AND engine LIKE '%MergeTree%'"

# Manually trigger TTL cleanup
kubectl exec clickhouse-shard0-0 -n oip -c clickhouse -- \
  clickhouse-client --password '<password>' --query \
  "OPTIMIZE TABLE system.trace_log FINAL"
